# Architecture

Slipstream uses one `NEAppProxyProvider` for both app scopes. iOS owns app attribution, flow diversion and on-demand reconnection; it hands the provider each protected app's TCP and UDP flows. The provider relays them through the Rust engine, which speaks HTTP CONNECT or SOCKS5 to the selected proxy using tun2proxy's handshake code. Unlike the packet tunnel of releases before 0.7.0, this creates no network interface, so no `utun` appears in an app's scoped proxy settings, interface list or default path. HTTPS remains end-to-end encrypted; no certificate installation, TLS interception, proxy preference, or injected app hook is used.

## Components

- `app/`: SwiftUI controls and the fixed-purpose setuid helper. The app runs as mobile and exchanges bounded JSON over anonymous pipes. iOS 14 lacks the Swift concurrency runtime, so the app bundles Xcode's back-deployment copy; iOS 15 and later load the system copy first. The app links it strongly because rootful iOS 14 jailbreaks trust only an app's strong launch dependencies.
- `src/main.rs`, `lifecycle.rs`, `control.rs`, `store.rs`: the root CLI, its lifecycle commands and the app's management API. `profiles.rs` holds the saved proxy lists and the selected proxy; `app_routing.rs` decides which apps are routed. Files under `etc/slipstream` in the install prefix (`/var/jb` rootless, `/` rootful) remain root-owned and private. The prefix is fixed at build time by `SLIPSTREAM_SCHEME`.
- `src/tunnel.m`, called through `src/native.rs`: the private, privileged iOS configuration adapter. It creates a per-app VPN configuration of the app-proxy type, persists its UUID before saving, checks that UUID and name before every operation, and controls only that configuration. It also sends the connected provider its reload and check messages. When a change needs a new provider, acknowledgement also checks for a newly started owned provider process, because on-demand reconnect can skip a sampled Disconnected state. Private API availability is checked at runtime. `src/app_catalog.m` lists installed apps and whether a per-app rule can name them.
- `provider/AppProxyProvider.m`: accepts flows and bridges each one to the engine through a Unix socket pair: a stream for TCP, datagrams for UDP. A Network.framework monitor selects a physical underlay and prohibits tunnel/loopback paths.
- `src/engine.rs`: the HTTP CONNECT / SOCKS5 relay on a two-worker Tokio runtime, DNS over TCP, SOCKS5 UDP ASSOCIATE, cancellation and, with `check.rs`, the connection check. `ProxyConnector`, added to tun2proxy by the local patch, performs the proxy handshake with tun2proxy's existing HTTP (Basic and Digest) and SOCKS5 code.

There is no Slipstream routing daemon, PF ruleset, hand-written NECP policy, executable-UUID catalog, launchd descriptor escrow, route-repair loop, or global Skywalk/netagent change in this backend. The app catalog reads installed app names and native per-app eligibility when the picker opens.

## Routing policy

**Selected apps** uses native app rules by signing identifier. Slipstream's own app is included so its exit-IP check follows the protected path. Unselected apps keep their normal connection. The picker lists only apps the user installed: bundle IDs outside Apple's `com.apple.` namespace that are not hidden. Apple's apps are not offered; several of them, including Safari, Mail and Calendar, could only be matched with domain/account restrictions anyway. An installed app that requires such restrictions is labeled and cannot be selected. Empty/wildcard Safari rules saved successfully but failed the actual packet audit during earlier research.

**All apps** has no device-wide equivalent in an app proxy: `includeAllNetworks` and its local-network, APNs and cellular exceptions belong to packet tunnels. The CLI instead names every app the user installed that per-app rules allow without domain restrictions, by the same rule as the picker. Apple's apps, including Safari, hidden system apps and system daemons keep their normal connection, and an app installed later is covered from the next restart or proxy change. There is no local-network exception; protected apps reach LAN addresses only through the proxy. SSH to the phone is unaffected because daemons are never matched.

TCP flows carry their destination as an address or, for connections by hostname, a name that the proxy resolves. The provider opens a TCP flow only after the engine reports that the proxy accepted the CONNECT, so a refused destination fails the app's connect instead of connecting and closing. UDP datagrams travel with their remote endpoint, encoded as a SOCKS5 address. DNS to port 53 becomes DNS over TCP through the proxy, to the queried resolver when it is public and otherwise to `8.8.8.8:53`; the provider also supplies `8.8.8.8` as its DNS setting. With an HTTP proxy, the engine refuses any other UDP flow when it opens, so QUIC falls back to TCP. With a SOCKS5 proxy, each other UDP flow opens a UDP ASSOCIATE control connection and a relay socket; a refused ASSOCIATE ends that flow without a direct fallback. Returning NO for a flow closes it; an app proxy never sends a flow direct.

Upstream TCP and UDP sockets bind to the current physical interface, so they cannot enter another VPN's tunnel. Interface index zero refuses new connections, and the provider waits up to two seconds for its first path before accepting flows. It uses the physical interface its path reports without requiring a satisfied status. The provider has no unbound fallback. It accepts at most 128 concurrent flows and closes further ones; socket buffers bound each flow, and a full UDP queue drops datagrams. It ignores `SIGPIPE`, so a write to a closed peer fails with `EPIPE` rather than ending the process.

## Lifecycle and status

The selected proxy is part of the saved lists in `proxies.json`; the CLI routes through it. The native configuration is journaled in `tunnel.uuid`. Enable saves the configuration and explicitly starts its session. Changes never stop the session: iOS treats a stop like the user turning the VPN off and lets traffic go direct until the next start. A proxy switch, restart or scope change saves the configuration while connected, which leaves the session running, and asks the provider to switch proxies in place. The provider ends its current flows so apps reconnect through the new proxy; saved app rules take effect without a new provider. iOS answers the request only after applying the saved rules; with a rule for each of 218 system and user apps that took up to 11 seconds, so the CLI waits 15. Other Network Extension calls also wait up to 15 seconds, because iOS can take several seconds to answer while it relaunches its daemons. A package upgrade needs a new provider, so the CLI kills the running providers and starts the new session.

Scope changes reuse the owned UUID. Disable removes that exact configuration, then clears the journal and enabled marker. A failed or uncertain operation retains the journal for reconciliation. The enabled marker records a pending change until the change completes, preventing an old connection from being reported as a completed proxy switch.

`protected` means the native configuration is enabled and its session is Connected. It does not mean the upstream proxy is healthy. Reconnecting sessions report `starting`; a requested but inactive/missing configuration reports `unavailable`. The app's HTTPS exit-IP request separately checks connectivity. Closing the app does not stop the provider.

For Test Connection, the CLI asks the connected provider to check its proxy through `NETunnelProviderSession` messaging, finding the session with `NEAppProxyProviderManager`, as it does for a reload. The engine opens a fresh TCP connection to the current proxy, bound to the current physical interface, and allows three seconds for the handshake. For a SOCKS5 proxy it then opens a second connection, authenticates, and sends UDP ASSOCIATE from an unspecified endpoint; the reply code becomes the app's UDP result (`relayed` or `unsupported`). HTTP proxies report `blocked` without a probe. No additional routing exception is installed. This check excludes DNS, HTTP authentication, app startup and the independent exit-IP request.

Apple documents app-rule behavior while disconnected. These API semantics do not prove every OS release, existing-flow transition, app update, or privileged bypass. Device captures and the limits of each test belong in the validation records. Neither native nor legacy routing is a security boundary against another root process. Flow diversion itself remains observable, for example through URLSession metrics and a private socket option.

## Configuration and privilege boundary

The app helper accepts root administration, or mobile only when its direct parent is the installed, root-owned, non-writable Slipstream executable. It clears groups/environment and executes `slipstream manage` with a deadline. It accepts no arbitrary executable, provider message or network destination. There is no HTTP server, credential-bearing command argument, shell evaluation of user input, or remote management port.

The management API uses a closed action enum, locks and atomic mode-600 files. Existing proxy lists, IDs, selected proxy, credentials and app settings keep their formats. Earlier releases also copied the selected proxy into `config.json`, which is no longer read. The authorized app displays saved credentials, so management responses and screenshots must stay private. Explicit disable remains available when proxy-list parsing fails.

The extension is registered inside the app and signed with its own app-proxy identifier (`local.slipstream.app.proxy`) and `app-proxy-provider` entitlement. The root CLI has private Network Extension configuration privileges, which require the jailbreak. It signs as the app (`local.slipstream.app`): iOS 14 assigns a saved configuration to the process that saves it, and provider messages through the public API only find configurations owned by the app. No Developer account registration or provisioning change was made. The app proxy has been verified live on the XS/iOS 18.5, the iPhone 11/iOS 14.8.1 and the iPhone 7/iOS 15.8.3.

## Upgrades

Upgrades keep the configuration and enabled preference, and replace the running provider. The package refuses to upgrade a release before 0.7.0: remove the old package, or install 0.7.1 first. Direct-domain exceptions are removed. Historical tests of PF, Skywalk and descriptor escrow describe earlier releases, not this architecture.
